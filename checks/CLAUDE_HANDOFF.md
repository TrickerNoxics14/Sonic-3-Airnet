## Stage C: relay fallback (Claude, 2026-11-11, code only, never deployed)

## Claude addendum 2026-11-14 (online play in the browser, nothing published, nothing deployed)

### Choice and reasons
Browsers have no UDP, so the browser build plays through a **relay server that speaks WebSocket to browsers and UDP to Windows games and forwards the very same datagrams between them** (`checks/relay_ws`). Options considered:
- *WebRTC data channels* (peer to peer): still needs a signalling server plus STUN/TURN, and a Windows game would need a WebRTC stack. Much more code, and the relay remains the fallback anyway.
- *A WebSocket-only relay*: Windows players would need a new transport.
- *The existing C++ relay with a WebSocket part*: needs its own SHA-1/handshake/framing in C++ with sockets code for two platforms; harder to host for free than a Node program.
- **Chosen**: the existing relay protocol (RelayProtocol.h v2, unchanged) carried in binary WebSocket messages, one message = one datagram. The engine already had a relay layer one level below the lobby (`UDPSocket::startRelay`, made-up peer addresses 240.0.x.y), so the browser change is only a new datagram transport underneath it. Handshake with the code proof, lobby, input delay, characters, state transfer and repairs are all the unchanged engine code. The Node relay (`relay_core.mjs`) is a faithful port of `RelayCore.h` (same limits, host secret, wrong-key block) plus a dependency-free RFC 6455 server (`ws.mjs`), `/health`, Origin list, proxy mode, ping/pong. No npm packages, Node 18+, Dockerfile.

### Engine changes (stable fork; Windows behaviour unchanged unless noted)
- `Sockets.cpp/.h`: under `__EMSCRIPTEN__` a `UDPSocket` has no real socket; the relay datagrams go through an emscripten WebSocket (`WebTransport`), inbox queue, reconnect with 0.5..8 s backoff, new join/registration after each reconnect. `UDPSocket::setRelayWebSocketURL`. New `getRelayRejoinCount` (all platforms): the friend counts how often the relay gave it a different token.
- `NetplayManager`: relay URL for the browser from `?relay=` in the page link, then the saved setting `Online.RelayServer`, then `window.S3AIR_RELAY_DEFAULT` (`relay_config.js`); `normalizeRelayWebSocketURL` (NetplayLobbyLogic.h, core-tested) makes `wss://` by default, `ws://` for localhost; `startJoinViaRelayOnly` (no game server, no direct attempt); the browser never contacts the game server (no external address query). Test switch `S3AIR_NO_SERVER` (hooks only) does the same for a Windows game.
- Compatibility key: `getActiveModsInfo()` used `__DATE__ __TIME__`, so no two compiles (a browser and a Windows build of the same source included) could play together. Now `NETPLAY_COMPATIBILITY_ID = "airnet-1"` (NetplayManager.cpp): **bump it whenever a change alters the simulation or the netplay protocol** (this relaxes the old "every compile is incompatible" rule on purpose; the game version number and the mod fingerprint are still compared).
- Lobby (browser only): ONLINE LOBBY opens; entry RELAY SERVER edits the address; CREATE LOBBY / JOIN WITH CODE refuse with a plain message when no relay is set; lobby codes only (join codes with an address need UDP); host sees "Cannot reach the relay server" after 10 s. Log lines `Lobby: screen X`, `Menu: main menu`, `Lobby: no relay server set`, `Lobby: cannot reach the relay server` (what the checks wait for).
- Input delay for a relayed line (all platforms, only when a friend is relayed): `autoInputDelayRelayed` = ping above 20 ms plus twice the measured deviation (`PingTracker::getDeviation`), at least 1 frame, at most 6; a fixed setting is untouched; direct connections keep the old rule. Reason: a browser WebSocket is TCP, one lost packet holds back everything behind it.
- Reconnect (bug, see below): friend restarts its game connection when the relay gave it a new place, and treats 10 s of silence from the host during a relayed game as a lost connection (existing 90 s reconnect then the plain message).

### Codes (exact format and reasoning)
* **Lobby code:** 6 digits, 100000 to 999999, random from the OS generator, unique among live lobbies, not reused for 5 minutes after a lobby closed. It is only a handle: the server answers with the 12 digit session ID, and everything else (secret, relay lobby, key, LAN tag) is derived from that ID by the existing challenge/response, so no secret is typed.
* **Long code (no server of ours needed: LAN, matchmaking server, relay by code):** 12 digit session ID in [10^11, 10^12) plus a Damm check digit = 13 digits, shown `1234-5678-90123`. Every single wrong digit and every swapped neighbour pair is detected (tested exhaustively). About 39.7 bits of secret, protected by the existing key stretching.
* **Collisions / guessing:** 900,000 codes; a blind guess hits a live lobby with probability (live lobbies)/900,000 (about 1 in 9,000 with 100 live lobbies). One address gets about 5 guesses per 6 minutes; a /24 about 25. One address needs years for a specific lobby; a large botnet (1000 addresses in 250 networks) could find one specific private lobby in a few hours with a low probability (about 10 percent in 2 hours). So: the 6 digit code of a private lobby is as private as the way it is shared; for stronger privacy use the long code (LAN GAME / matchmaking path). Public lobbies are public by definition. The operator of the lobby server can see lobby names and session IDs and could join any lobby (same trust as any relay). A longer private code is a server setting away (`codeDigits`) but the game's menu accepts exactly 6 or 13 digits today.
* **The old join code (IP + port + secret, letters)** is unchanged, used only by the F9 window and tests; the ONLINE menu never creates or reads it. **Letters are gone from every code a player sees or types** (guard test: "codes contain only digits"). Older versions: a 1.2.1 host's letter code cannot be typed in 1.3 and the other way round; the game packets are unchanged.
* **NETPLAY_COMPATIBILITY_ID stays `airnet-1`:** the simulation and the game packets did not change; lobby, directory and code changes are above that level. The lobby list marks lobbies as OTHER by a hash of the same version-and-mods text that the join check compares.

## Claude addendum 2026-11-15 (direct WebRTC connections between browsers, relay stays lobby, signalling and fallback; nothing published, pushed or deployed). NOTE (browser-multiplayer branch): written BEFORE the lobby directory/menu work and merged onto it afterwards; the test numbers below are from the old base and the web_net session P is re-verified on the merged base in a later task.

### Design and reasons
- **Where it plugs in:** `UDPSocket` (oxygen_netcore/network/Sockets.cpp). The game already talks to relayed peers through made-up addresses (240.0.x.y); the new layer decides per peer whether a datagram leaves through the relay or through a direct channel. Everything above (handshake with the code proof, lobby, lockstep, repairs) is unchanged and still checked end to end. The topology is a star (host and friends), so direct channels exist only host <-> friend (host sees friend N as peer N, a friend sees the host as peer 0).
- **Channel:** one WebRTC data channel `s3air`, `ordered:false, maxRetransmits:0` (UDP-like, no head-of-line blocking, which is what the relay's TCP WebSocket cannot give). Datagrams above 16000 bytes go through the relay.
- **Signalling:** new relay message types `SIGNAL_C2R/R2C/H2R/R2H` = 10..13 (RelayProtocol.h, relay_ws/protocol.mjs), same layout as the data messages, protocol version stays 2. Relay needs no new server, counts them apart (`signals`), caps 3000 bytes, 20/s per friend and direction, never reads them. Old relays and old games drop unknown types, so old and new clients still share a lobby and old clients simply stay on the relay. Payload = 1 kind byte (offer, answer, candidate, end, bye) + text (SDP / candidate JSON). The friend offers, the host only answers. Trickle ICE.
- **Fallback and liveness (the important part):** the channel carries the game only while BOTH directions work: each side sends a 2-byte keep-alive every 250 ms that says "I hear you"; a side uses the channel only if it heard the peer within 2 s AND the peer's last keep-alive said it hears us. Reason: a one-way failure (found while designing; a silently dropped direction) would otherwise lose everything the healthy direction still sends. No traffic for 5 s on an open channel, no connection within 8 s, or a close event = failed, and the friend asks again (12 s after one that worked and died; 12 s x (1 + failures), at most 96 s, for one that never worked, e.g. a host that cannot do WebRTC). Receiving always accepts both paths.
- **Why no extra sequence numbers:** switching paths can reorder or repeat a datagram, but the netcode was written for UDP already: tracked packets carry unique ids and are deduplicated (`ReceivedPacketCache`), input packets carry frame numbers and older ones are ignored (`mLastReceivedFrameNumber`, NetplayHost.cpp), state transfer is tracked. P4 below shows no desync across 3 switch-overs.
- **Compatibility id NOT bumped** (`airnet-1`): the simulation and the game packets did not change, the signalling is relay level.
- **Privacy:** a direct connection shows each player's IP address to the other player (a relay-only game shows it only to the relay operator). Off switches: `?p2p=off`, settings `Online.DirectConnection=false`, `S3AIR_P2P=false` in relay_config.js. STUN default: two public Google STUN servers (`Online.StunServers`, `?stun=`, `S3AIR_STUN_SERVERS`, `none`). Tests use `?stun=none` (no external contact). No TURN: networks STUN cannot cross stay on the relay.
- **Lobby/log:** friend lobby shows "Direct connection to the host (peer to peer)." when a channel is in use, host's "plays through the relay" warning and auto input delay count only friends that are really relayed. Browser online log has a `[p2p] transport=p2p|relay direct_in/out relay_in/out` line (browser only, so Windows log parsers are unaffected). Console lines: `Netplay: direct connection to the host is in use (p2p)`, `... is not working (any more), back on the relay server`, `Netplay (browser): direct connection to peer N did not work / lost (...)`.
- No third-party library was added for phase 1 (the browser's own WebRTC), so the third-party notices are unchanged.
